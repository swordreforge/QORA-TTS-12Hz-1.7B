> 本文件 CSV 与阶段耗时是实测资产，予以保留；但 §5 与 §2/§3 中的**归因和工具建议是黑盒推测**，以下逐条纠正，施工时不要按原文走：
>
> 1. **RAYON_NUM_THREADS / OMP / OpenBLAS 全部无效**：本仓库是纯 `std::thread` + 手写 AVX2 核（`src/simd.rs`、`src/gpool.rs`），没用任何并行运行时/BLAS。调线程的旋钮只有 `QORA_THREADS` 和 `taskset`（均已实测）。
> 2. **Attention 不是热点**：perf 实测 98%+ 周期在 Q4 GEMV + 因果/转置卷积；这种序列长度下 FlashAttention、KV-int8 化收益为零。长块 per-frame 变慢（0.14→0.24）是事实，但归因"查 KV 实现"方向偏了。
> 3. **21s prefill / 2x decode 毛刺是环境的**：24 分钟长跑中的 CPU 争抢、E 核调度与散热墙，非算法问题。缓解靠 `taskset` + 安静机器；prefix-cache 落地后暴露面也随之消失。
> 4. **Warmup 已经是链式的**（prev-chunk tail 12 帧，不是 ref），剩余 ~3% 要动 streaming decoder 重构，ROI 不足，已延期。"缓存 ref 中间状态"不要做。
> 5. **量化状态已知**：talker Q4（1511MB/1.7B），手写 AVX2 核；本机无 AVX-512（运行时 dispatch，永不触发）。"检查 AVX-512/int8 GEMM"类建议跳过。
> 6. **施工顺序**（有依赖）：① 前缀 KV 缓存（已落地，-3%，见 8）→ ② 合并短句（已落地，默认 t80，-10%，见 9）→ ③ allocator/LTO 先测量再要（已测，见 10）→ ④ iGPU/量化不出本次 scope。
> 10. **P1 allocator/LTO 已测（2026-09-30，two2 单块对照，输出 sha256 全程一致）**：thin→fat LTO 约 -5%（20.5s→19.3s，主要 prefill 7.2→6.7s），构建 46s，一行配置，**保留**；mimalloc 再 -0~1.5%（噪声级），且它是 C 代码（破 pure-Rust 立项），**已回退**。大 tensor 预分配：当前大头是逐帧/逐层 Vec 分配，但 allocator 实测无感，说明分配不是瓶颈，**不做**。
> 11. **P2 裁决（2026-09-30，精度版图已查）**：talker Q4 + predictor Q4（compress 双双 `use_q4=true`）+ AVX2 手写核 = 已到屋顶；**唯 speech decoder 是 f32**（`save_decoder` 全 `write_f32_vec_io`，占 31% wall）——P2 量化只剩这一块有结构性 headroom，但要破 bit-exact（耳验+HNR 门禁重验，且 vocoder 对量化敏感），是数天级项目，需单独立项。PGO 已实测：19.7s vs 19.3s（≈0%，另一次 33s 是已知的环境 gen 毛刺），**不采用**（双阶段构建 + profile 保鲜负担，零收益不配）。CPU 跨块流水线（decode N 与 gen N+1 重叠）：同核争抢 + 有状态共享复杂，上限 ~10%，defer。iGPU：**否决**——可用栈（OpenVINO/ORT）全是 C++（破立项），wgpu+WGSL 手写是周级移植 + 共享内存争抢 + 丢 bit-exact，且 decode 仅 31%，Amdahl 上限 ~25%。P2 结论：无低 hanging fruit；真要继续，唯一候选是 decoder-Q4（先立项再动手）。
> 12. **decoder-Q4 立项已关闭（2026-09-30，门禁 0 实测未过，零代码改动）**：241f decode-only，DRAM 读 123GB vs decoder f32 权重 ~130MB → 权重占比 **0.1%**（门禁要 20%）；42f/241f 双长度计时 3.2s vs 27.4s，外推固定截距 ≈0（权重一次性成本归零，超线性的是 activation）。量化权重省 100MB/123GB，无意义；decode 带宽利用率仅 ~2GB/s（延迟 bound），int8 同样无收益。详见 `docs/decoder-q4-plan.md` §8。CPU 推理优化到此收工：剩余 wall 全是逐帧 activation 铁账，P/E 核全开 + 安静机器即最优形态。
> 13. **P/E 调度已测、无事可做（2026-09-30，零代码改动）**：缺页 204k 全 minor（≈1%，新鲜 Vec 置零）、dTLB ≈0.01s、migrations=0、THP 已是 always——命中/缺页 avenue 合计 ~1%，madvise/affinity 不配动手。worker 数：默认 22 全核即最优（two2：全核 19.5s vs P-only 23.4s；decode241：全核 29.5s vs P+E 29.2s，LP-E 排除是噪声）。旧"P-only 最快（18.3s）"结论过期（thin-LTO 时代 + 均分 barrier 前提，overdecomp 后已死）。README hybrid-CPU 节已按今值重写；`QORA_THREADS` 只留作让核用，不作加速用。
> 14. **iGPU 代理实测（2026-09-30，OV benchmark_app，MTL Arc）**：bert-small（transformer 代理）CPU 295ms/20FPS → GPU 38ms/105FPS（**5~7x**）；conv 代理未测（OMZ 现货多为待转换格式，torch 链太重，2D conv 对 1D Vocos 本来也只是上界参考）。解读：Arc 跑全并行小模型确实快，但我们的 decode 是 123GB activation、延迟 bound（§12），和 bert-small（小权重、compute bound）形状相反，**数字不可迁移**；唯一 conclusive 的测试是转我们自己的 decoder（需 torch 复刻，数天级 spike）。iGPU 维持 buried，原否决理由（C++ 栈、移植税、Amdahl 上限）不变。工具链：`/opt/intel/openvino`（setupvars.sh），benchmark_app 已编好在 `/tmp/opencode/ovbuild/intel64/`（另：uv 的 openvino-dev 自带一个现成的）。
> 15. **GPT 第二阶段评审落地（2026-09-30，拆指标实测）**：generation done 行已拆 talker/predictor 分项（`generate_new.rs`，常开）。two2/54f：talker 3.6s（67ms/f）vs predictor 4.3s（80ms/f）——**predictor 占 54%**。结构已验：predictor = prefill2 + 14 AR 步 × 5 层（`code_predictor.rs:218`），耗时比 1.19 ≈ 参数量比估算 1.24 → 是实打实的算量，无同步浪费、无布局 bug，微优化只剩每步 alloc 复用（个位数 %）。KV 算术：talker 每帧 KV 读约 46MB（T=200）vs 权重 ~1100MB ≈ 4% → KV 布局工作无意义；predictor KV ≤16 项 → 无。decoder 写放大确认真实（123GB/241f + 超线性），是唯一剩的有 headroom 项 → 下一步先做 pass-count 插桩定量（不动手写融合，先数）。PMU 警告：`cpu_core/LLC-load-misses` 只见 demand-miss，streaming 权重流量（prefetcher 搬运）不可见——绝对值只看数量级，split 时钟比才是硬信号。
> 16. **decoder 真货开箱（2026-09-30，decode 内部分项，计时插桩零行为变更、sha 验证一致）**：241f decode-only 26.4s = transformer 0.8s（3%）+ upsample 1.3s（5%）+ **vocos-blocks 24.0s（91%）** + other 0.2s。各块形状：b0 [768,7712] / b1 [384,38560] / b2 [192,154240] / b3 [96,462720]（44M floats = 177MB/tensor）。执行图毛病清单（静态可见）：（1）ConvNeXt pw1/pw2 是逐 t gather→f32_gemv（标量单线程）→scatter，audio-rate 下每 stage 数十万次调用 + input_t 分配；（2）每 residual unit 一次 signal.clone() 全张量 memcpy（每 block 3 次）；（3）snake_beta 每次返回新 Vec（每 block 6+ 次全张量写）；（4）causal_conv1d 每次 thread::scope 现 spaw 线程；（5）decoder-tf 逐 t f32_gemv（单线程，13.5k calls）但只占 0.8s——明确不碰（3% 不配）。动刀顺序：vocos elementwise 融合+原地化（snake/clone/add）→ pw 批 GEMM 化 → conv spawn 复用；门禁沿用 tolerance+耳验（求和顺序必变，overdecomp 先例）。分块计时：b0 3.6s（14%）/ b1 5.6s（22%）/ b2 7.7s（30%）/ b3 8.4s（33%）——b3 并未如元素数预估占 47%，b0 单位元素最贵（overhead 主导），b2+b3 合 63%。
> 17. **phase-1 已回退（2026-09-30，零收益）**：snake 原地化（去 memset）+ residual clone 改 move，全 bit-exact、差分测试过，241f 三跑：24.0s/25.4s/36.5s（后一个是环境毛刺）vs 基线 24.0~25.2s——**零可测收益，已全部 revert**（只计时器保留）。教训：memset/clone 这些 pass 落在 cache-hot 快路径上（~1%），真正的 pass 成本是 conv MAC + snake 超越函数（sin/exp 逐元素，compute 主导）+ per-op spawn。下一步真刀：snake 近似/向量化、pw 批 GEMM、spawn 复用——全部破 bit-exact，走 tolerance+耳验。是否动手，等拍板。
> 18. **conv tiling 落地（2026-09-30，bit-exact，sha 三跑一致）**：causal conv macro（exact/FMA 同体）+ scalar 镜像加 length-tiling（tile=256K/ic，逐元素累加顺序不动，天然精确；大尺寸差分测试覆盖多 tile/非对齐边）。 241f：b0 3.6→3.3 / b1 5.6→4.6 / b2 7.7→5.2 / b3 8.4→4.2，blocks 25.2→17.3s（-31%），decode 27.7→19.7s（-29%）。教训：首跑 b3 曾 16.9s（恰为 2x 环境毛刺形状），复跑 4.2s 才定案——单跑会杀死真优化，复跑是铁律。tile 尺寸未调优（262144/ic 拍脑袋，E 核 L2 下仍成立）；transpose/depthwise 未动（同病，相近预期）。
> 8. **P0 前缀缓存已落地并纠正预期（2026-09-30 实测）**：① 只 cache 了 `9+R`（约 38/151，ICL 把本块文本揉进 block 前部，171 并非完全相同——原文"完全相同"有误）；② suffix-prefill 6.1s vs 全量 7.2s，prefill 是 overhead-dominated 非长度线性，**实测仅省 ~1.2s/块，长文档约 -3%**，不是 §2 预估的 -19%/250~350s。实现 bit-exact（同 seed 开/关 sha256 一致），默认开（`--no-prefix-cache` 回退）。真正的 P0 大头是**合并短 chunk**（每消灭一块省整个 8s prefill + decode）。
> 9. **短块合并已落地（2026-09-30 实测，sub8 对照：8 句/687 帧同内容）**：unmerged 287s（RTF 5.24）→ merge-t120 275s（5.01，-4%）→ merge-t80 244s（4.72，**-10%**)。教训：decode 单帧成本随块长爬升（~86 帧 0.11s → ~215 帧 0.12s → ~340 帧 0.18s，疑似 Vocos 巨型 activation 的内存搬运），吃掉了 t120 大部分 prefill 红利；t80（~200 帧/块）是甜点。默认 `merge_target=80`，cap 150（帧估算 chars×2.8，实测 2.3~2.6+余量，500 码上限内安全；小 max-codes 自动缩 cap/禁用）。附带收益：接缝 38→~18（长文档），每个接缝都是一次 glitch 风险。`--merge-target N` / `--no-merge-chunks` 可调。待耳朵验收长块漂移。
> 7. 术语：RTF 5.14x 即 0.19x realtime（RTF>1 = 慢于实时），全文统一按 RTF 表述。

## 3. 异常点，profiling 重点看这些

### 3.1 Prefill 异常慢

正常 prefill 约 **7.5~8.3s**，但下面这些 chunk 到了 **20~22s**：

| Chunk | Prefill | 正常值 | 倍数 |
|---|---:|---:|---:|
| 4 | 21.2s | ~8s | 2.6x |
| 9 | 21.0s | ~8s | 2.6x |
| 13 | 21.0s | ~8s | 2.6x |
| 24 | 21.9s | ~8s | 2.7x |
| 30 | 20.6s | ~8s | 2.5x |

这些不是文本长度导致，文本都不长。更像：

- CPU 线程池同步/争抢
- 内存分配或 cache 逐出
- 频率降频
- 与上一块 decode 结束后的资源释放冲突

建议 profiling 时单独抓这几个 chunk 的 `perf`。

---

正常 decode 约 **0.09~0.10s/timestep**，但下面这些明显异常：

|---|---:|---:|---:|---|

| 16 | 21.8s | 103 | 0.212 | 约 2x |

这些块生成帧数不多，但 decode 时间很高。重点查：

- Vocos 大张量分配/释放
- 卷积内核线程数

## 4. 每个 Chunk 重复的固定日志

这些行几乎每块都一样，是最大浪费来源：

```text
ICL mode: ref_text 35 tokens, ref_codes 16x161, block 162, remainder 0
Voice embedding norm=17.1930, injected with TTS_PAD overlay at position 4
Prefill done in X, position=171
```

说明每块都重新 prefill 到 **position=171**，参考前缀完全相同。

从 Chunk 2 开始还有：

```text
Decoder warmup: chained 12 frames (prev chunk tail)
Decoder warmup: 12 ref frames prepended
Decoder warmup trimmed: 23040 samples (12/N frames)
```

每块额外解码 12 帧再裁掉。39 块累计多出约 **456 个 decode timestep**，按 0.1s/timestep 估算浪费 **45~60s**。

## 6. 一句话结论

Profiling 优先盯三块：

1. **每块重复 prefill 到 position=171**：正常 8s × 39 ≈ 312s，异常块到 21s，总 prefill 388.8s。
2. **每块 decoder warmup 12 帧再裁掉**：约浪费 50~60s。
3. **短 chunk 太多 + 长 chunk attention 变慢**：短块 RTF 可到 8~11，长块每帧耗时从 0.14s 涨到 0.24s。

最大优化点仍然是：**缓存 ICL/voice 前缀 KV cache、合并短 chunk、复用 decoder warmup。**
整体看，这次不是“模型加载慢”，而是 **39 个 chunk 串行推理 + 每个 chunk 都重复做大量固定工作** 导致的。日志里集成显卡没有参与计算，完全是 CPU 路径。按日志粗算：

- 39 个 chunk，总输出音频约 **278.9s**
- 推理总耗时约 **1433s ≈ 23.9 分钟**
- 实时率 RTF ≈ **1433 / 278.9 ≈ 5.14x**，即生成 1 秒音频要 5 秒多
- 模型加载只有 **0.483s / 1511MB**，不是瓶颈
- 阶段占比大致：
  - Prefill：**388.8s，27.1%**
  - Talker generation：**592.4s，41.3%**
  - Speech decode/Vocos：**450.8s，31.5%**

核心结论：**最大优化点是复用每个 chunk 完全相同的 ICL/voice 前缀，其次减少 chunk 数、复用 decoder warmup、调线程和量化内核。iGPU 最适合接 Speech decoder/Vocos。**

## 1. 关键日志现象

每个 chunk 都有：

```text
ICL mode: ref_text 35 tokens, ref_codes 16x161, block 162, remainder 0
Voice embedding norm=17.1930, injected with TTS_PAD overlay at position 4
Prefill done in 8.x s, position=171
```

也就是说：

- 参考文本 35 tokens
- 参考 codes 16x161，block 162
- voice embedding 每次都相同，norm=17.1930
- 每个 chunk 都重新 prefill 到 position=171

但 39 个 chunk 的参考前缀完全相同。现在每块都重新算一遍，这是巨大浪费。

Prefill 大多数是 **8.1~8.3s**，但有些异常到 **20~22s**：

- Chunk 4：21.2s
- Chunk 9：21.0s
- Chunk 13：21.0s
- Chunk 24：21.9s
- Chunk 30：20.6s

这些异常不是文本长度导致的，更像 CPU 调度、频率、内存分配、线程池同步或缓存逐出问题。

Generation 总 592.4s，平均每帧约 **0.17s/frame**。长 chunk 明显更慢：

- 33 帧：4.7s ≈ 0.142s/frame
- 186 帧：42.5s ≈ 0.228s/frame
- 181 帧：40.6s ≈ 0.224s/frame
- 160 帧：37.1s ≈ 0.232s/frame

说明自回归上下文变长后，attention/KV cache 成本上升。

Decode 总 450.8s，正常约 **0.09~0.10s/timestep**，但异常块会到 **0.2~0.39s/timestep**。并且每个 chunk 从第 2 块开始都有：

```text
Decoder warmup: chained 12 frames
Decoder warmup: 12 ref frames prepended
Decoder warmup trimmed: 23040 samples
```

这相当于每块多解码 12 帧再裁掉。39 块累计多出约 456 个 decode timestep，占总 decode timestep 约 11.6%，大约浪费 **50~60s**。

## 2. 优化优先级

### P0：缓存/复用 ICL prefix，收益最大

现在每块 prefill 固定 171 位置，参考文本、参考 codes、voice embedding 完全一样。理想情况下：

- 进程启动后只计算一次 ref_text + ref_codes + voice embedding 的 talker KV cache
- 每个 chunk 只 prefill 新文本 token
- 从 position=171 继续生成

预计效果：

- 每块 prefill 从 8s 降到 1~2s 甚至更低
- 39 块可省 **250~350s**
- 总时间直接下降 20% 以上

实现要点：

- 保存 talker 前 171 位置的 K/V cache
- 保持位置编码正确，新文本从 171 开始
- 如果 Rust 代码里 KV cache 是每块新建，需要改成可复用对象
- 如果 voice profile 每块重新注入，也可以缓存 embedding 和注入后的 prefix

这是最值得做的优化。

---

### P0：减少 chunk 数，合并短句

现在 result.txt 被切成 39 chunks，很多非常短：

- 6 chars、10 chars、12 chars、13 chars、16 chars、19 chars 等
- Chunk 29 只有 6 chars，总耗时 14.4s，音频 1.7s，RTF 约 8.5

每个 chunk 的固定成本包括：

- prefill 约 8s
- decoder warmup 12 帧
- EOS 生成、调度、分配、保存

建议：

- 按语义合并短句，尽量接近 max codes 500 或模型上下文上限
- 保持每块 100~200 帧以上，减少固定开销
- 如果质量允许，39 chunks 合并到 10~15 chunks，能省大量 prefill 和 warmup

预计收益：**100~300s**，实现成本低。

---

### P1：去掉或复用 decoder warmup

日志里每块都：

```text
Decoder warmup: chained 12 frames
Decoder warmup: 12 ref frames prepended
Decoder warmup trimmed: 23040 samples
```

每块额外解码 12 帧，再裁掉。可以尝试：

- 第一块之后不再 prepend ref 12 帧，直接用前一块尾部状态
- 缓存 ref 帧的 pre-conv / transformer / Vocos 中间状态
- 如果 decoder 是卷积结构，保留波形上下文，而不是重新解码再裁剪

预计节省 decode 时间 **10~15%**，约 **50~60s**。

---

### P1：线程和 CPU 调优

日志显示：

```text
System: 31570 MB RAM, 22 threads
```

22 threads 很可能是逻辑核数，包含超线程。纯 CPU 矩阵乘/卷积不一定线程越多越好，线程同步和内存带宽会拖累。

建议测试：

```bash
RAYON_NUM_THREADS=8
RAYON_NUM_THREADS=12
RAYON_NUM_THREADS=16
OMP_NUM_THREADS=...
OPENBLAS_NUM_THREADS=...
```

并用 `taskset` 绑定物理核：

```bash
taskset -c 0-15 target/release/qora-tts ...
```

同时：

- 电源模式设为 performance
- 关闭后台任务
- 如果多 NUMA，用 `numactl --interleave=all`
- 用 `perf stat -d` 看 IPC、缓存未命中、内存带宽
- 用 `cargo flamegraph` 看热点是 attention、GEMM 还是 Vocos 卷积

预计收益：**10~30%**，尤其能缓解那些 20s prefill 和 20s decode 的异常块。

---

### P1：编译与内存分配优化

你已经用了：

```bash
RUSTFLAGS="-C target-cpu=native" cargo run --release
```

可以再加：

```bash
RUSTFLAGS="-C target-cpu=native -C opt-level=3 -C lto=fat -C codegen-units=1"
```

如果项目允许，使用：

- `mimalloc` 或 `jemalloc`
- 预分配/复用大 tensor 缓冲区
- 避免每块重新分配 `[512, T]`、`[1024, T]`、`[1536, T]`、`[96, 289920]` 这类大张量
- 使用内存池或 arena

日志里 Vocos block 3 出现：

```text
Vocos block 3: [96, 289920]
```

这种大张量频繁分配/释放会明显增加延迟，尤其异常 decode 块。

---

### P2：量化与内核优化

模型权重加载 1511MB，对 1.7B 参数约 0.89 B/参数，看起来已经是 int8 或混合量化。继续量化的空间不一定大，但可以检查：

- 是否启用 AVX2 / AVX-512 / VNNI / BF16
- 是否使用 int8 GEMM
- attention 是否有 FlashAttention 类似优化
- KV cache 是否可 int8 量化
- Vocos 卷积是否用 oneDNN / OpenBLAS / 自研 SIMD

如果是纯 Rust 自研内核，优先优化：

- GEMM
- attention
- 卷积
- 内存拷贝

预计收益：**20~40%**，取决于当前内核质量。

---

### P2：iGPU 加速 Speech decoder / Vocos

日志完全没有 GPU 调用，集成显卡没参与。最适合放 iGPU 的是：

- VQ codebook lookup
- pre-conv
- speech decoder 8 层 transformer
- Vocos 上采样和卷积

原因：

- 这些是规则卷积/矩阵运算，并行度高
- 不依赖自回归逐帧采样
- Vocos 输出张量很大，GPU 更合适

可选路线：

- Vulkan / wgpu 实现 Vocos 前向
- OpenCL / oneAPI / OpenVINO
- ONNX Runtime + OpenVINO EP
- 把 speech decoder 单独导出成 ONNX，用 iGPU 跑

注意：iGPU 共享内存带宽，如果同时 CPU 跑 talker，可能竞争内存。建议：

- talker 留 CPU
- decode/Vocos 放 iGPU
- 或者流水线：CPU 生成下一块，iGPU 解码当前块

预计 decode 可从 450s 降到 100~200s，但移植成本较高。

---

### P2：生成与解码流水线

当前是串行：

```text
prefill -> generate -> decode -> 下一块 prefill -> ...
```

可以尝试：

- 当前 chunk 在 decode 时，下一 chunk 做 prefill
- 当前 chunk 在 decode 时，下一 chunk 做 talker generation
- 但纯 CPU 下会争抢核心，需要实验线程分配

如果 decode 放 iGPU，流水线收益会很大。

---

## 3. 建议的优化顺序

1. **缓存 ICL prefix / voice embedding / ref codes 的 KV cache**
2. **合并短 chunk，减少 chunk 数**
3. **复用 decoder warmup，去掉每块 12 ref frames 重复解码**
4. **线程数调优：8/12/16 物理核测试，绑定核心**
5. **预分配/复用大 tensor，换 mimalloc**
6. **加 LTO、PGO、检查 AVX-512/VNNI**
7. **把 Vocos/speech decoder 放 iGPU 或 OpenVINO**
8. **模型层面：减少 talker 层、蒸馏、更小 vocoder**

---

## 4. 预期效果

如果只做 P0：

- 缓存 ICL prefix
- 合并 chunk
- 复用 warmup

可能从 **24 分钟降到 12~15 分钟**，RTF 从 5.1 降到 2.5~3.0。

如果再加上：

- 线程调优
- 量化内核优化
- iGPU 跑 Vocos

有机会降到 **8~12 分钟**，RTF 接近 2 左右。

当前最大瓶颈不是模型加载，也不是编译，而是：

> **每块重复 prefill 171 位置 + 每块重复 decoder warmup + 39 个 chunk 串行执行。**

优先解决这三个，收益最直接。
